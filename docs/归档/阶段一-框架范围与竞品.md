## 1. 定位

**内容中台 = 企业对外内容的结构化管理与供给层。** 下接事实与素材（知识库、PIM/ERP、外部 DAM/网盘），中间是 CMS（建模、编辑、AI 生产、审核、版本），上面通过 API / MCP / Webhook 把内容供给各个平台和 Agent。

```
        内容使用方：AI 门户/官网 · SEO/GEO Agent · SDR Agent · 社媒 Agent · 电商平台 · 经销商门户 · 外部 Agent
                                      ▲  Delivery API / Preview API / MCP / Webhook
 ┌──────────────────────────── 内容中台 ────────────────────────────┐
 │  供给：调用方与授权范围 · 渠道格式（JSON / Markdown / JSON-LD） · 调用留痕             │
 │  CMS（核心）：内容模型 · 编辑器 · AI 生产 · 多语种 · 审批与发布检查 · 版本与发布 · 内容组织   │
 │  事实：录入/维护 · 冲突检测与处理 · 引用与影响分析     资产库：本地上传 · 导入副本 · 来源追踪  │
 │  集成层：连接器 · 拉取入库 · 来源追踪 · 同步状态 · 变更通知                                     │
 └──────────────▲──────────────────────────────────▲─────────────┘

          企业知识库（KDH）                外部 DAM · 网盘 · 飞书/SharePoint · PIM · 对象存储
```

## 2. 集成模式：拉取入库（D8–D10）

### 2.1 总原则

对接任何外部系统（知识库、DAM、网盘、PIM…）都用同一个模式：**拉取 → 存入 CMS 对应位置 → 本地使用 → 持续同步**。

| 外部来源 | 存到 CMS 的哪里 | 存什么 |
|---|---|---|
| 知识库：结构化事实 | 事实库 | 事实全部字段（取值、单位、证据等级、有效期、适用范围） |
| 知识库：文档与片段（生成时检索到的） | 内容版本的"生成依据" | 被用到的片段原文 + 出处 |
| DAM / 网盘 / 飞书 / PIM 的素材 | 资产库 | 文件副本 + 元数据 + 授权信息 |

每条入库数据都带同一组**来源追踪字段**：

`来源系统` · `外部 ID` · `外部版本/修改时间` · `入库时间` · `最近同步时间` · `同步状态` · `本地是否修改过`

**同步状态**：已同步 ／ 源已更新（本地未跟上）／ 本地已修改（未推回）／ 双方都改了（冲突）／ 源已删除 ／ 同步失败

**这个模式解决的问题**：外部链接失效、源系统停机、源系统权限变化时，CMS 里的内容仍然能编辑、生成、预览和下发。

**需要同时守住的三条线**
1. **副本不等于授权**：素材授权到期、源系统标记撤回时，即使本地有副本也必须拦截（发布检查不通过、Delivery API 不下发）。
2. **副本会变旧**：源已更新但本地未跟上时要显示出来，事实类的差异进入复核，不能默默用旧值。
3. **源被删除不等于本地删除**：本地副本保留并标记"源已删除"，已发布内容不受影响，新引用需要确认。

### 2.2 事实的双向编辑（D10）

中台和知识库都可以修改同一条事实，所以需要**同步规则**，否则会互相覆盖或来回同步（回环）。

**规则**
- 每条事实有**版本号**；双方各自记录"上次同步时的版本"。
- 自上次同步以来**只有一方改了** → 自动同步到另一方。
- **双方都改了** → 不自动覆盖，进入冲突处理面板（第 3 节第 ⑤ 类），由事实负责人选。
- 同步时带上"修改来源"标识，收到自己发出的变更不再回推，避免回环。
- 可按**属性类别**设置同步方向（参考 HubSpot 与 Salesforce 的字段级同步规则）：
  - 双向（默认）
  - 以知识库为准（如认证、检测类：知识库侧有专人维护）
  - 以中台为准（如营销卖点、对外表述）
  - 对方为空时才写入
- 知识库修改了**已被已发布内容引用**的事实 → 同步到中台后，引用它的内容进入复核（同 3.5 的规则）。
- 同步失败或知识库尚未确认的事实标记"未同步"，可以用于草稿，不能用于对外发布。

### 2.3 从知识库取内容生成（D9）

1. 生成时按模板和范围，从**本地事实库**取结构化事实（已同步的副本，速度快、不怕断连）。
2. 需要背景材料时（案例、应用场景、技术说明），**实时检索知识库**；知识库不可用时退回只用本地事实生成，并提示。
3. 生成结果保存时，把**用到的事实 ID 和检索到的片段原文**一起存进该内容版本的"生成依据"。之后即使知识库里的文档被删改，这篇内容仍然能说清楚"当时依据的是什么"，审核也能逐条核对。

## 3. 事实冲突：检测与处理

### 3.1 冲突类型

| 类型 | 例子 | 检测方式 | 何时检测 |
|---|---|---|---|
| ① 事实 vs 事实 | BL-R600 防护等级：IP66（TÜV 报告）/ IP65（2024 手册） | 同一 `对象 + 属性`、取值不同（单位归一后比较） | 录入、同步合并 |
| ② 内容 vs 事实 | 正文写"IP65"，事实库里是 IP66 | AI 从正文抽取声明，与事实比对 | 保存草稿、送审 |
| ③ 内容 vs 内容 | 两篇已生效内容写了不同的交付周期 | 对已生效内容做声明抽取并交叉比对 | 定期巡检 |
| ④ 时效 | UL 证书已过期，内容仍在引用 | 有效期到期 | 每日定时 |
| ⑤ 同步冲突 | 中台把交付周期改成 8 周，同期知识库改成 12 周 | 双方版本都比上次同步时新 | 每次同步 |

### 3.2 先排除"假冲突"

很多取值不同其实是**适用范围不同**，不是冲突。判定冲突前先比较以下维度，只要任一维度能区分开，就提示"拆分为不同适用范围"，而不是报冲突：

- 型号/配置（标准版 vs 防爆版）
- 区域/市场（欧盟 vs 北美）
- 测试标准/条件（IEC vs UL；额定 vs 峰值）
- 生效时间（旧版手册 vs 新版报告：属于"版本更替"）

### 3.3 推荐选择规则（参考 MDM 的"存活规则"）

系统按顺序给出推荐值，用户确认后生效。规则顺序可按企业、按属性类别配置：

1. **属性的权威来源优先**：例如 认证类 → 证书/检测报告；规格类 → PIM；交付周期 → ERP。
2. **证据等级高者优先**：A > B > C。
3. **生效日期新者优先**。
4. 以上都无法决定 → **交给事实负责人人工决定**。

### 3.4 处理动作

在冲突处理面板中，并排展示两条取值、来源原件、证据等级、有效期，以及**各自被哪些内容引用**，可执行：

| 动作 | 结果 |
|---|---|
| 采纳 A | B 标记为"已被替代"（保留历史，不再可引用） |
| 拆分适用范围 | 两条都保留，补上区分维度（型号/区域/标准） |
| 都暂停 | 两条都不可用于对外发布，直到补齐证据 |
| 发起源系统修正 | 源系统事实只读时，生成修正任务给源系统负责人 |

**处理完成后**：结果同步到 KDH 并记录决策（谁、何时、依据）；引用了被替代取值的内容自动进入**复核队列**。

**未处理期间**：冲突事实可以出现在草稿里（带警示），但**发布检查不通过**，Delivery API 不会下发引用它的新版本。

### 3.5 内容里怎么引用事实

建议用**事实插槽**，而不是把取值复制进正文：

- 编辑器里插入的是带事实 ID 的"事实标签"，渲染时取当前值；
- **参数表、规格卡**这类结构化位置：事实更新后**自动刷新**，只需记录；
- **正文叙述**：事实更新后不自动改写，进入复核队列，由编辑确认；
- 发布时，引用的事实取值随内容版本做快照，便于回溯。

## 4. 资产库与 DAM 对接（D3、D11 细化）

### 4.1 资产库：一个库，两种来源

CMS 自带资产库，**本地上传**和**从外部导入的副本**放在一起管理，用"来源"区分：

| 来源 | 说明 | 可编辑性 |
|---|---|---|
| 本地上传 | 没有接 DAM 的客户直接在这里维护 | 全部可编辑 |
| 导入副本（默认） | 从 DAM/网盘/飞书/PIM 拉取文件存到本地对象存储，带来源追踪（2.1） | 文件跟随源系统同步；本地可补充内容侧字段（alt、多语种标题、使用说明） |
| 仅引用（可选） | 只存外部 ID 和地址，不存文件 | 适用于客户要求素材"只能存在原 DAM"的情况，按连接器单独开启 |

资产库的基础能力：文件夹与标签、搜索、预览、多尺寸裁切、授权信息（版权、可用区域与渠道、到期日）、被哪些内容引用、和内容一样走审核。打标、转码、去重这类深度能力仍然留给专业 DAM，CMS 只做够用的部分。

### 4.2 资产记录字段

来源 · 外部 ID · 外部版本 · 文件类型 · 尺寸/时长 · 标题/描述/alt（可多语种）· 标签 · **授权信息** · 引用它的内容列表 · 同步状态（见 2.1）

### 4.3 连接器接口规范（每个外部库实现同一套）

| 能力 | 说明 |
|---|---|
| 鉴权 | OAuth / API Key；**沿用源系统的权限**，用户在中台只能看到自己在源系统有权限的资产 |
| 浏览与搜索 | 目录浏览、关键词搜索；源系统支持时透传语义搜索 |
| 取元数据 | 标题、标签、授权、版本 |
| 取渲染地址 | 原图/缩略图/指定尺寸；视频封面与播放地址 |
| 变更通知 | Webhook 或定时轮询：资产更新、删除、授权变化 |

### 4.4 首批连接器建议
- 通用：S3 兼容对象存储、URL 引用
- 国内办公：飞书云文档/云空间、钉钉、企业微信微盘
- 海外：SharePoint/OneDrive、Google Drive
- DAM：特赞 MuseDAM、Bynder、Cloudinary（按客户实际情况选）
- PIM：Pimcore、Akeneo（产品图与规格书）

### 4.5 同步与跟踪
- 源资产更新 → 资产标记"源已更新"，按连接器配置自动拉取新版本，或由人确认后替换；
- 源资产删除 → 本地副本保留并标记"源已删除"，已发布内容不受影响，新引用需确认；
- 授权到期或源系统撤回 → **无论本地有没有副本**，引用它的内容都进入复核，发布检查拦截；
- 本地上传的资产以后可以"迁移到 DAM"：推送到 DAM 后转为导入副本，内容引用不变。

## 6. 竞品参考（按 v2 范围重排）

### 6.0 竞品在"集成模式"上怎么做（对照 D8–D11）

| 我们的做法 | 竞品做法 | 结论 |
|---|---|---|
| 从知识库拉取并存到本地，用于生成 | **Contentstack Knowledge Vault**：上传 PDF/TXT 后抽取文本存储（不存原文件），供 AI 生成使用，也可通过 API 写入。**Writer Knowledge Graph**：通过连接器接入 Google Drive、SharePoint、Confluence、Notion，同步并建索引，管理员可重新索引 | **主流做法**：AI 生成依赖的知识都先入库建索引，而不是每次去源系统现取 |
| 外部素材复制到 CMS 资产库 | **Contentful + Bynder**：只在条目的 JSON 字段里存资产数据和 Bynder 的 CDN 地址，Bynder 出新版本时自动更新——**引用模式**。**Contentstack**：自带 Assets 资产库（上传、整理、复用、走审核），同时提供 Bynder、Brandfolder、Acquia DAM 等连接 | 海外头部 CMS **对正规 DAM 多用引用**，因为要保持素材唯一来源和授权管理；**自带资产库 + DAM 连接**是标配。我们默认复制、可选引用，比它们更抗断连，但要补上授权与版本跟踪（2.1 的三条线） |
| CMS 自带资产库 | Contentstack Assets、HubSpot 文件管理器、Storyblok 资产管理、Strapi 媒体库都内置 | **标配**，合理 |
| 事实在中台和知识库两边都能改 | **HubSpot 与 Salesforce 双向同步**：按字段设置同步规则（双向 / 始终以某方为准 / 某方为空才写入），并警告重复映射会造成覆盖和同步回环 | 可行，但必须有**字段级同步规则 + 版本号 + 双方都改时进冲突队列**（2.2），否则会互相覆盖 |

### 6.1 CMS 核心：重点拆解
- ⭐ **Contentstack**：Agent OS + Brand Kit + Knowledge Vault，"创作时强制、审批时校验"——最接近我们"事实约束 + 发布检查"的整体思路。拆：内容模型、品牌规则执行、发布批次与环境。
- ⭐ **Contentful**：托管 MCP（含语义搜索、AI Actions）、per-space / per-environment 权限、内容模型与组件化。拆：内容模型设计、调用方与环境、MCP 工具设计。
- ⭐ **Sanity**：AI 生成结果必须通过 schema 校验；Content Agent。拆：结构化生成。
- **Storyblok**：MCP 三级权限（readonly / execute / destructive）、Agent 只能在用户权限内行动、可自带模型。拆：MCP 权限模型。
- **Kontent.ai**：AI 按准则复核内容（禁用词、语调、可读性）；ISO 42001。拆：Brand Voice 规则化。
- ⭐ **HubSpot Content Hub**：背景文档的蓝本。只取内容生产部分：Content Remix、Brand Voice、Breeze 知识库；建站部分不在范围。

### 6.2 事实与冲突处理
- ⭐ **Aprimo**：Compliance Agent 对照已批准素材做声明校验——对应我们的"内容 vs 事实"检测。
- **Salsify / Akeneo**：只把**已批准**的产品属性通过 MCP 暴露给 Agent；Salsify 能从产品数据自动生成 Q&A。
- **Pimcore**：Agent 走与人相同的校验和审批（Agent SDK）。
- **MDM 存活规则**（Informatica MDM、Stibo STEP 等主数据产品的通用做法）：按来源优先级、时间、完整度自动选出"黄金记录"——第 3.3 节规则的来源。

### 6.3 DAM 对接（作为连接器对象和交互参考）
- **Cloudinary**：Search Agent 只返回"已审批 + 已授权 + 可投放"的素材——引用时的过滤规则可借鉴。
- **特赞 MuseDAM**：国内首批连接器候选。
- **Bynder / Frontify / Acquia DAM**：权限沿用、读写分离、访问日志。
- 交互参考：Contentful、Storyblok 的外部 DAM 插件（在编辑器内选取外部资产）。

### 6.4 GEO 输出（只取内容侧）
- **Optimizely / Progress Sitefinity**：Q&A 字段、全量 Schema.org JSON-LD。附录结论：llms.txt 97% 零请求，不必押注。

## 7. 下一轮待讨论

1. **D4 回灌知识库**：生效内容是否、以什么形态回灌 KDH？（建议：仅指定类型，如 FAQ、案例；作为候选知识，由 KDH 侧确认）
2. **同步方向的默认值**：2.2 中哪些属性类别默认"以知识库为准"、哪些"以中台为准"？
3. **规则配置权**：3.3 的冲突选择规则和 2.2 的同步方向，由平台给默认值、每个客户调整，还是每个属性类别单独配？
4. **副本存储**：视频等大文件也复制吗？（建议：设大小上限，超过的视频默认"仅引用"，或只存封面与转码后的分发版本）
5. **D5 / D6 / D7**：生产深度、首批使用方、部署形态。

| 原型现状 | v2 调整 |
|---|---|
| 企业事实库只读展示 + 冲突提示 | 增加录入与编辑、KDH 同步状态、**冲突处理面板**（3.4 节的四种动作与影响内容列表） |
